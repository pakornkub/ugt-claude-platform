# Data scope + สายอนุมัติ — "ทำได้ไหม" กับ "กับข้อมูลของใคร"

RBAC ตอบได้คำถามเดียว: **ผู้ใช้คนนี้ทำสิ่งนี้ได้ไหม** — `leave:read` มีหรือไม่มี

แต่แทบทุกหน้าถามคำถามที่สอง: **กับข้อมูลของใคร** หัวหน้าเห็นของลูกน้อง พนักงาน
เห็นแต่ของตัวเอง HR เห็นทั้งบริษัท ทั้งสามคนมี `leave:read` เหมือนกันหมด

การมีแค่ข้อแรกคือช่องโหว่ที่พบบ่อยที่สุดในระบบภายในองค์กร: ผู้ใช้ผ่าน guard ทุกด่าน
แล้วแก้ `?empCode=` ใน URL เป็นของคนอื่น ก็เห็นข้อมูลคนอื่น ทั้งที่ระบบ "ตรวจสิทธิ์แล้ว"

## กฎเหล็ก

> **ทุกหน้า / route / Server Action ที่รับ `empCode` (หรือรหัสเจ้าของแถวอื่นใด)
> เข้ามาจากภายนอก ต้อง resolve scope แล้วตรวจก่อนแตะข้อมูล**
> ค่าใน URL, body, หรือ hidden field ไม่ใช่หลักฐานว่าผู้ใช้มีสิทธิ์กับแถวนั้น

## รูปแบบการใช้

```ts
// รายตัว — เช่นหน้า detail ที่รับ ?empCode=
const scope = await resolveDataScope(session.user.id, PERMISSIONS.LEAVE_READ_ALL);
if (!isEmpCodeAllowed(scope, empCode)) return notFound();   // 404 ไม่ใช่ 403

// รายการ — เช่นตาราง
const rows = await prisma.leaveRequest.findMany({
  where: { ...scopeWhere(scope), status: 'pending' },
});
```

**ทั้งสองแบบต้องมาจาก scope ก้อนเดียวกัน** ถ้าตารางกรองด้วยชุดหนึ่งแต่หน้า detail
ตรวจด้วยอีกชุดหนึ่ง ช่องว่างระหว่างสองชุดคือช่องโหว่ และเป็นช่องโหว่ที่ไม่มีใครเห็น
เพราะหน้าจอดูถูกต้องดี

**ตอบ 404 ไม่ใช่ 403** สำหรับแถวที่ไม่อยู่ใน scope — 403 ยืนยันว่ารหัสนั้นมีอยู่จริง

## ลำดับการตัดสิน

```
viewAll (permission <resource>:read-all)  → ผ่านทุกแถว
ownEmpCode ตรงกัน                          → ผ่าน
อยู่ใน subordinateEmpCodes                 → ผ่าน
นอกนั้น                                     → ไม่ผ่าน
```

บัญชีที่ยังไม่ผูกกับพนักงาน (`ownEmpCode = null`) **เห็นอะไรไม่ได้เลย** ซึ่งเป็นทิศ
ที่ปลอดภัย — และ `scopeWhere` คืน `{ in: [] }` ซึ่งคือศูนย์แถว ไม่ใช่ทุกแถว

## permission naming

scope ต้องมีคู่ของมันในรายการ permission เสมอ:

| key | ความหมาย |
| --- | --- |
| `<resource>:read` | เข้าหน้านี้ได้ |
| `<resource>:read-all` | เห็นได้ทุกคน ไม่จำกัดแค่ตัวเอง+ลูกน้อง |

ไม่มี `:read-all` = ทุกคนเห็นแต่ของตัวเอง ซึ่งเป็นค่าเริ่มต้นที่ปลอดภัย

## สายอนุมัติ (`lib/approval-chain.ts`)

คนละเรื่องกับ scope: scope ตอบว่า *อ่าน* อะไรได้ สายอนุมัติตอบว่า *คำขอนี้ต้อง
ไปหาใคร*

- อ่านจาก view สิทธิ์อนุมัติขององค์กร — หนึ่งแถวต่อหนึ่งขั้น (`EmpCode` + `Seq`)
- **ไม่ใช่ตัวเดียวกับ `superEmpCode`** บน view พนักงาน ซึ่งเป็นหัวหน้าสายตรง
  ชั้นเดียวแบบ denormalize สายอนุมัติจริงมีหลายขั้นและอาจไม่ใช่หัวหน้าสายตรง
  ใช้ `superEmpCode` แทนได้เฉพาะตอนทำ scope "ทีมของฉัน" เท่านั้น

### พังคนละแบบ โดยตั้งใจ

| ไฟล์ | ตอน query ล้ม | เพราะ |
| --- | --- | --- |
| `lib/directory.ts` | คืน `null` / `[]` **เงียบ** | ทำงานระหว่าง login — ฐานพนักงานล่มต้องไม่แปลว่าทุกคนเข้าระบบไม่ได้ |
| `lib/approval-chain.ts` | **โยน exception ต่อ** | คืน `[]` เงียบ ๆ แปลว่าคำขอถูกบันทึกโดยไม่มีผู้อนุมัติ ผู้ใช้เห็นว่า "ส่งแล้ว" แล้วมันค้างจนมีคนมาทวงในอีกสองสัปดาห์ |

`getOrgUnits()` เป็นข้อยกเว้นในไฟล์หลัง — พังเงียบได้ เพราะเป็นแค่ตัวเลือกใน
ดรอปดาวน์ ไม่ใช่คำตอบว่าคำขอไปหาใคร

### แยกให้ออกระหว่าง "ไม่มีสาย" กับ "ระบบล่ม"

`getApprovalChain` คืน `[]` เมื่อพนักงานรายนั้น**ยังไม่ถูกตั้งสายอนุมัติจริง ๆ**
ผู้เรียกต้องแยกสองกรณีนี้ให้ผู้ใช้:

- `[]` → "ยังไม่ได้ตั้งผู้อนุมัติของคุณ กรุณาติดต่อฝ่ายบุคคล"
- โยน exception → "ระบบขัดข้อง กรุณาลองใหม่"

รวมสองอันเป็นข้อความเดียวคือการส่งคนไปหา HR ทั้งที่แค่ linked server ล่ม

## ตอนติดตั้ง

1. แทน `__HR_AUTHORIZE_VIEW__` (คนละ view กับของ `lib/directory.ts`) และแม็ป
   คอลัมน์ `EmpCode` / `Seq` / `SuperEmpCode` / ชื่อผู้อนุมัติ / `OrgCode3` /
   `OrgTDesc3` ให้ตรงของจริง
2. เพิ่ม `<resource>:read-all` ลง `lib/permissions.ts` ให้ครบทุก resource ที่มี scope
3. โปรเจคที่ไม่มี workflow อนุมัติ — ลบ `lib/approval-chain.ts` ทิ้ง `lib/scope.ts`
   ไม่ได้พึ่งมัน

## ที่จงใจไม่สกัดมา

`ugt-hrms` มี `WorkflowResolverService` ที่ผูกสายอนุมัติกับ config ต่อเมนู,
snapshot สายอนุมัติ ณ เวลายื่นคำขอ, และการ fallback ไปหาหัวหน้าสายตรงเมื่อไม่มี
สายอนุมัติ — ทั้งหมดเป็นกติกาของ workflow ในโปรเจคนั้น ไม่ใช่มาตรฐานกลาง
สิ่งที่สกัดมาคือชั้นอ่านข้อมูลดิบเท่านั้น
