# Directory enrichment — ทำไม SSO/LDAP อย่างเดียวไม่พอ

SSO และ LDAP ตอบได้แค่คำถามเดียว: **"คุณคือใคร"** — username, อีเมล, ชื่อที่แสดง
จบแค่นั้น

แต่แทบทุกฟีเจอร์ในแอปองค์กรถามคำถามถัดไปทันที: รหัสพนักงานอะไร อยู่หน่วยงานไหน
ตำแหน่งอะไร หัวหน้าคือใคร ชื่อไทยสะกดยังไง — Keycloak ไม่รู้ AD ก็ไม่รู้
คำตอบอยู่ในฐานพนักงานกลางที่อ่านผ่าน **linked server**

ไม่มีชั้นนี้ ทุกฟีเจอร์จะไปต่อ view เองทีละที่ แล้วแม็ปคอลัมน์ไม่เหมือนกัน

## รูปแบบ

```
login (SSO หรือ LDAP)
  → getDirectoryPerson(loginName)        ← lib/directory.ts (SELECT อย่างเดียว)
  → directoryUserFields(person)
  → เขียนลงแถว user                       ← สำเนาไว้อ่านเร็ว ไม่ใช่ต้นฉบับ
```

ทั้งสองทาง login เรียก helper **ตัวเดียวกัน** โดยตั้งใจ ถ้าแยกกันเขียน ผู้ใช้ SSO
กับผู้ใช้ AD จะมีฟิลด์ไม่เท่ากัน และจะไม่มีใครรู้จนกว่าจะมีหน้าจอที่ต้องใช้ฟิลด์นั้น

| จุดเรียก | ไฟล์ |
| --- | --- |
| LDAP login | `lib/actions/auth.ts` → `ldapLoginAction` (ก่อน `prisma.user.upsert`) |
| SSO login | `lib/auth.ts` → `databaseHooks.session.create.after` |
| ตั้งบัญชี AD ล่วงหน้า | `lib/actions/admin-users.ts` → `addDirectoryUserAction` |

**SSO ต้องเติมใน session hook เท่านั้น** — Better Auth ไม่เก็บ custom field ที่คืน
จาก `mapProfileToUser` ให้ (มีแต่ name/email/image ที่รอด) เขียนไว้ตรงนั้นแล้วจะ
หายเงียบ ๆ

## กฎ

1. **แถว user เป็นสำเนา ไม่ใช่ต้นฉบับ** ต้นฉบับคือ view ฝั่ง HR แอปห้ามแก้ฟิลด์
   กลุ่มนี้เอง — แก้ไปก็โดนทับในการ login ครั้งถัดไป และระหว่างนั้นสองที่ไม่ตรงกัน
2. **เติมใหม่ทุกครั้งที่ login** ไม่ใช่ครั้งแรกครั้งเดียว คนย้ายหน่วยงาน เปลี่ยน
   ตำแหน่ง เปลี่ยนหัวหน้า ถ้าเติมครั้งเดียวตอนสมัคร ข้อมูลจะค้างอยู่ที่วันแรก
   ตลอดไป และไม่มีใครสังเกตเพราะมันดูเหมือนข้อมูลจริง
3. **ห้ามทำให้ login พังตาม** ทุกฟังก์ชันใน `lib/directory.ts` คืน `null`/`[]` เมื่อ
   query ล้ม ไม่โยน exception — ฐานพนักงานล่มแล้วทุกคน login ไม่ได้ แย่กว่าชื่อไทย
   หายไปชั่วคราวหลายเท่า
4. **SELECT อย่างเดียว** ห้าม INSERT/UPDATE/DELETE ข้าม linked server เด็ดขาด
   กฎการเขียน SQL ที่เหลือ (CAST ทุกคอลัมน์, ห้าม recursive CTE, pagination)
   อยู่ที่ `ugt-nextjs-database-setup` → `references/raw-sql-and-sp.md` ที่เดียว
5. **ชื่อ view และรายชื่อคอลัมน์ต้องผ่าน `Prisma.raw`** เพราะเป็นตัวระบุ ไม่ใช่ค่า
   ใส่เป็น `${...}` เฉย ๆ ใน `$queryRaw` จะกลายเป็น parameter แล้ว SQL พัง
   — และเพราะเป็น `raw` **ห้ามให้ค่าที่มาจากผู้ใช้เข้าไปในสองจุดนี้เด็ดขาด**
   ค่าจากผู้ใช้ส่งเป็น `${}` ปกติเท่านั้น
6. **ตรวจ format ตัวระบุก่อนเสมอ** (`/^[a-zA-Z0-9_.@-]+$/`) แม้จะส่งเป็น parameter
   แล้วก็ตาม — ค่าที่ผิดรูปแบบแปลว่ามีที่ไหนสักแห่งข้าม validation มา ควรรู้ตรงนี้
   ไม่ใช่ปล่อยให้ยิงข้ามเซิร์ฟเวอร์ไปก่อน
7. **คอลัมน์ที่ไม่มีใครอ่าน ให้ตัดทิ้ง** คอลัมน์ที่ไม่มีใครใช้คือคอลัมน์ที่ไม่มีใครรู้ว่า
   ค่ามันถูกหรือผิด

## ตอนติดตั้ง

1. แทน `__LINKED_SERVER__.__HR_DB__.dbo.__HR_EMPLOYEE_VIEW__` ด้วย view จริง
2. แม็ปชื่อคอลัมน์ใน `COLUMNS` ให้ตรงของจริง (`CAST(... AS ...) AS <ชื่อในโค้ด>`)
3. ตัดฟิลด์ที่โปรเจคไม่ใช้ออกจากทั้ง `DirectoryPerson`, `directoryUserFields`
   และ schema
4. ขอสิทธิ์ SELECT บน view ให้ service account ของแอป — ระบุลง
   `docs/admin-handoff.md` พร้อมกับเรื่อง Keycloak

## เมื่อโปรเจคไม่มีฐานพนักงานกลาง

ลบ `lib/directory.ts` กับจุดเรียกทั้งสาม แล้วตัดฟิลด์กลุ่มนี้ออกจาก schema
`addDirectoryUserAction` ก็ตัดไปด้วย (มันดึงชื่อ/อีเมลจาก directory) — ผู้ใช้ AD
ยังเกิดเองตอน bind สำเร็จครั้งแรกตามปกติ แค่กำหนด role ล่วงหน้าไม่ได้

## ที่จงใจไม่สกัดมาจาก HRMS

`ugt-hrms` มีหน้า `/admin/users/sync` ที่ดึงพนักงานทั้งหน่วยงานมาสร้างทีเดียว
พร้อมแม็ป role ตามคอลัมน์ในฝั่ง HR ไม่เอามาเพราะมันผูกกับสมมติฐานว่า view ฝั่ง HR
มีคอลัมน์บอก role อยู่แล้ว ซึ่งเป็นเรื่องขององค์กรนั้น ไม่ใช่มาตรฐานกลาง
โปรเจคที่ต้องการทำได้ด้วย `searchDirectory()` + วน `addDirectoryUserAction`
